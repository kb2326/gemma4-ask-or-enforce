# Asking vs. Adding a Stage: A Pre-Registered Held-Out Test of Prompt Rules and a Planning Stage for a Budget-Bound Gemma 4 Coding Agent

Draft 4, 2026-10-31, after an independent review of Draft 3. Tables between `TABLE` markers are generated by
`python analysis/paper_tables.py` from `experiments/*/results.csv` and `trace_stats.csv`; do not edit them by hand.
Limit: 3,000 words.

## Abstract

People who configure coding agents around open models usually cannot train the model. Two cheap levers remain:
what they tell it (prompt rules) and how they arrange it (agent structure). On Gemma 4 31B (4-bit, 4x L4) fixing
SWE-bench-style issues within 4.5 minutes and 100 tool calls per task, we designed arms on 30 development tasks,
then tested pre-registered claims once on 41 held-out tasks. A prompt rule was followed to the letter: scratch
scripts went to /tmp on every scratch-first task (held-out 20/20 vs 0/25, p < 0.001), while the behaviour it served,
editing source before writing scripts, showed no detectable change (+7 pp, 95% CI -7 to +22). A planning stage, a
localizer that cannot edit placed before an unchanged fixer, raised source-first starts on development tasks
(20% to 40% of tasks; per-task paired p = 0.009), but **this did not replicate on held-out tasks** (11/41 vs 10/41,
one-sided McNemar p = 0.50). The fixer itself was never constrained, and on development tasks handing over the
correct files raised source-first starts about as much, so the development gain may have come from location
information rather than structure. A tool-call limit written in the localizer's prompt was ignored (median 177 s of
the budget, one development run); removing the stage's tools bounds it by construction (11-14 s). Solve rates showed
no detectable difference across arms (10-14 of 41; the design detects only large differences). We report the failed
replication and a measurement error caught by review.

## 1. Introduction

In the Kaggle Gemma 4 Developer Agent competition, a coding agent is a declarative ADK YAML configuration
(prompts, sub-agents, tools, sampling) around an open model on modest hardware, with no custom code, no training of
the base model and a tight per-task budget.

To change an agent's behaviour, a configurator can **ask** (write a rule into the prompt) or **add structure**
(split the work into stages with different tools). Prior work suggests both matter (Section 6), but we know of no
study that compares them on the same model and tools, checks from transcripts whether the model did what it was
asked, and confirms the result on tasks not used for design.

Our contributions:

1. **Prompt rules are followed to the letter (confirmed).** The checkable part of a rule (where to put scripts) was
   obeyed every time; a change in the behaviour it served was not detected.
2. **A planning-stage effect seen on development tasks did not replicate on held-out tasks.** We show why it was
   fragile: the stage did not constrain the fixer, and location hints alone produced a similar development gain.
3. **Limits stated in a prompt were ignored; a stage without tools is bounded by construction.**
4. **No configuration produced a detectable change in solve rate,** most failures being timeouts.
5. **Two methodology lessons:** a path-based compliance metric gave a striking but false result until checked
   against raw transcripts; and behavioural effects found by iterating on 30 tasks need a held-out test.

## 2. Setting

**Model and serving.** Gemma 4 31B instruction-tuned, W4A16 QAT, served with vLLM 0.19.1 on 4x NVIDIA L4 (tensor
parallel 4), 32,768-token context. Temperature 0.2, top-p 0.95, at most 8,192 output tokens per step, thinking budget
4,096 tokens. The model is never trained: every run uses the competition sample submission's two LoRA adapters
unchanged.

**Harness.** The official harness (swegemma 0.2.11, adk_submission 0.2.13, google-adk 1.36.1) runs each task in a
sandbox with nine tools: shell, read, write, edit, status, submit and three code-graph tools. Per task the budget is
4.5 minutes of agent time and 100 tool calls; one shell command may run 120 s. If the agent stops without
submitting, the harness sends up to three "continue" nudges. The graded patch is the last submitted diff, or the
working tree. Grading runs hidden fail-to-pass and pass-to-pass tests, as in SWE-bench.

**A fixed budget.** Seconds depend on hardware, so we treat the limit as one instance of a fixed per-task budget.
Reference runs take a median of 19-23 model steps per task at about 8-10 s each, including tool time; 11 to 18 of
30 development tasks and 22 to 28 of 41 held-out tasks end by timeout in every arm.

**Tasks.** The competition provides 129 practice tasks from four repositories. We graded each task's gold patch
(must pass) and an empty patch (must fail), three times. 71 tasks passed (FastAPI 29, Rich 42); none of the 14
Requests and HTTPX tasks did (the gold patch failed in the sandbox, or the tests passed without it). We used 30 for
development (FastAPI 13, Rich 17) and held out the other 41 (FastAPI 16, Rich 25), never run while designing arms.
The hidden leaderboard tasks come from other repositories.

## 3. Method

**Arms.** Every arm differs from the reference in one design choice.

| Arm | Change from reference | Question |
|---|---|---|
| Reference (E2) | official sample prompt, one agent | — |
| E3.1 | prompt adds: first edit to source by step 8; put scratch scripts in /tmp; no reproduction scripts before the first source edit | Does asking change behaviour? |
| E5 | SequentialAgent: a localizer with read, shell and graph tools but no edit tools (prompt: stop after about 8 tool calls; reply with files, functions, plan), then a fixer with the reference prompt and tools | Does a planning stage change behaviour? |
| E5b | E5 with a tool-less localizer that answers once from the issue and the directory tree | Does a stage without tools stay short? |
| ORACLE | reference agent plus the gold source files as task hints (development: files and heuristic function names; held-out: files only) | Is finding the code the bottleneck? |

The fixer in E5/E5b keeps the reference prompt verbatim after a three-sentence preamble that points to the
localizer's notes and says to start by editing those locations. The fixer keeps all of the reference's tools: the
planning stage constrains only the localizer. The reference's helper sub-agent (called once in 185 task attempts
across our first runs) is not carried over.

**Measurements from transcripts.** Per task: solved; timeout; the first file write and its kind; /tmp use;
localizer time; and, for unsolved tasks, whether the final patch touched no source, only wrong files, or gold files. A write is a **source** write only if it targets a file inside a package
folder that is not a test or reproduction script; new files at the repository root, test files and anything under
/tmp are scratch. Shell redirects and `tee` count as writes after removing quoted strings and heredoc bodies.
**Source-first** means a task's first write was a source write; a task with no write counts as not source-first. We
report it over all tasks; the share among tasks that wrote anything is shown second, because an arm can change
whether the agent writes at all (E5 wrote on only 13 of 30 tasks).

**Development phase (exploratory).** Arms were run one to three times on the 30 development tasks, with predictions
committed before each run. To count each task once, we average an arm's runs per task and compare per-task means
with the reference's (three runs, solved 11, 12, 13) by a one-sided sign-flip permutation test and a task-level
bootstrap 95% interval. Arms were added after seeing earlier results (E5b after E5) on the same tasks.

**Held-out confirmation (pre-registered).** Before any held-out run, we committed the claims, the analysis code and
an amendment from an independent methodology review that set the tests below. Each arm ran once on the 41 held-out
tasks from notebooks built from one commit. Claims were tested in a fixed sequence, each at one-sided alpha 0.05,
stopping at the first failure:

- **C1 (manipulation check of asking):** among scratch-first tasks, E3.1 puts the script under /tmp in at least 80%,
  E2 in at most 20%, Fisher p < 0.05.
- **C2 (primary):** per task, source-first in E5b vs E2, one-sided exact McNemar p < 0.05; manipulation check: E5b
  localizer median at most 60 s. Expected power was about 0.6, so a null result is reported as "not detected".
- **C3:** the one-sided 95% bootstrap upper bound of the ORACLE minus E2 solve-rate difference is below +15 pp.

Tasks with a harness failure in any arm would be dropped; none occurred.

**C1 passed: rules are followed to the letter.** On held-out tasks E3.1 put every scratch-first script under /tmp
(20/20), the reference none (0/25). A change in the behaviour the rule served was not detected: source-first 13/41
vs 10/41 (+7.3 pp, 95% CI -7.3 to +22.0).

**C2 failed: the planning-stage effect did not replicate.** E5b started with a source edit on 11 of 41 tasks, the
reference on 10 (5 tasks favoured E5b, 4 the reference; p = 0.50). The manipulation check was met: the localizer took
a median of 13.8 s, leaving the fixer almost the whole budget, yet the fixer still wrote a scratch script first on 20
of 41 tasks. Per repository the direction was mixed (FastAPI 6 vs 4, Rich 5 vs 6). E5b did not differ from ORACLE
either (-2.4 pp, CI -14.6 to +9.8).

**C3 not tested.** The sequence stopped at C2, so C3 is not claimed. As an estimate only, ORACLE (files only, unlike
the development ORACLE) solved 12/41 vs the reference's 14/41 (-4.9 pp, one-sided upper bound +2.4 pp).

**Solve rates.** Held-out solves were 14, 13, 10 and 12 of 41. With 41 tasks and one run per arm only differences of
roughly 20 pp or more are detectable, and none appeared on either set. Most unsolved tasks ran out of time (22 to 28
timeouts) or ended with no source edit (15 to 19), rather than editing only wrong files (0 to 2).

**Graph search vs grep (development only).** Using code names from each issue and no model, the competition's
`search_similar_code` put every gold file in its top five for 8 of 30 tasks, grep for 11 (together 15), so by our
pre-registered rule the graph-first arm was not run.

**A measurement error caught by review.** Our first definition counted any write outside /tmp as a source write,
which made E3.1 look like a dramatic backfire (scratch-first on 30 of 50 writing tasks vs 0 of 70). It was an
artifact: the reference agent's scripts lived at the repository root. An independent review of raw transcripts
caught it; all numbers here use the corrected definition.

## 5. Discussion

**Why did the development effect vanish?** One held-out run per arm cannot settle it, but the development data
offer a clue. Handing the reference agent the correct files raised source-first starts almost as much as the
planning stage did (+16.7 vs +20.0 pp), and E5b's fixer receives location notes plus an instruction to start by
editing them. The development gain may therefore have come from location information and that instruction, not from
the stage split; on held-out tasks neither helped (E5b and ORACLE within 1 task of each other). Selection adds to
this: E5b was designed after seeing E5 on the same 30 tasks. The reference itself stayed stable (20% of development tasks, 24% of held-out).

**What held up.** Literal compliance replicated exactly, and stage length was controlled only by removing tools,
not by the prompt's limit. The behaviour we hoped to shift is a habit of the fixer, which kept its tools. A real test of
enforcement would constrain the fixer, for example a first fixer stage with edit tools but no shell, so the first
write cannot be a script; this needs new runs and we leave it to future work.

**For practitioners.** Put hard limits in structure; expect prompt rules to be followed in their checkable letter;
do not expect stage splits or location hints to lift solve rates when most failures are timeouts.

## 6. Related work

SWE-bench (Jimenez et al., 2310.06770) defines the task format. Agentless (2407.01489) fixes localization, repair and
validation as stages and matches agent systems with strong models. SWE-agent (2405.15793) shows that agent-computer
interface design substantially improves performance. SWE-Gym (2412.21139) reports that zero-shot open 7-32B models
do far better in a specialised workflow than as general agents. AgentIF (2505.16944) finds weak compliance with
constraints in agent prompts; our C1 adds that checkable constraints can be followed exactly while their purpose is
not served. SWE-Effi (2509.09853) evaluates software agents under token and time budgets and highlights expensive
failures, matching our timeout-dominated failures. LocAgent (2503.09089) shows graph-guided localization works with strong models and, after
fine-tuning, with open 7-32B models, with keyword search contributing most. SHERLOC (2606.24820) finds injected
diagnostic localization helps models near 30B; our ORACLE gives files only, without diagnosis, and under a binding
budget. Statistics follow Miller (2411.00640).

## 7. Limitations

One held-out run per arm on 41 tasks from two repositories: power for C2 was about 0.6 at the development effect
size, so a smaller real effect could be missed. Development comparisons are exploratory and include a data-driven
arm (E5b). C2 mixes a tool-less first stage, location notes and an instruction to start by editing them; the fixer's
preamble says the localizer read the code, which is not true for E5b. E5 ran once, so the prompt-limit failure rests
on one development run. The development reference pools a first run with a larger output limit (16,384 tokens). The "source" definition is a
path heuristic, revised once after review. vLLM sampling is not deterministic: two identical reference runs
disagreed on 3 of 30 tasks. The two held-out pairs ran about four hours apart (Kaggle allows two GPU sessions at
once). One model and one budget; the practice repositories are not the leaderboard repositories.

## 8. Conclusion

For a 4-bit 31B open model under a fixed budget, prompt rules are followed to the letter, and a stage without tools
stays short where a prompt limit does not. But a planning stage that seemed to change the fixer's habit on 30
development tasks did not on 41 held-out tasks, plausibly because the fixer was never constrained and the
development gain came from location hints. No configuration changed solve rate detectably. The most reliable
lessons are methodological: check compliance metrics against raw transcripts, count each task once, and confirm
development effects on held-out tasks with tests fixed in advance.
