# Ask or Enforce? A Pre-Registered Test of Prompt Rules and Agent Structure for a Small Open Model under a Fixed Budget

Draft 3, 2026-10-31, after the held-out runs. Tables between `TABLE` markers are generated by
`python analysis/paper_tables.py` from `experiments/*/results.csv` and `trace_stats.csv`; do not edit them by hand.
Limit: 3,000 words.

## Abstract

People who configure coding agents around small open models usually cannot train the model. They have two cheap
levers: what they tell it (the prompt) and how they arrange it (the agent's structure). We compared the two on
Gemma 4 31B (4-bit) solving SWE-bench-style tasks under a fixed budget of 4.5 minutes and 100 tool calls per task,
designing on 30 development tasks and then testing pre-registered claims once on 41 held-out tasks. Asking was
followed literally: a prompt rule to put scratch scripts in /tmp was obeyed on every scratch-first task in both sets
(held-out 20/20 vs 0/25, p < 0.001), but the behaviour the rule was for, editing source before writing scripts,
moved little. On the development set, enforcing the intent structurally, with a localizer stage that cannot edit
before the fixer, raised the share of writing tasks whose first write was a source edit from 26% to 55-60%. **This
did not replicate on held-out tasks**: 11/41 vs 10/41 tasks (one-sided McNemar p = 0.50). One structural effect was
robust: a time limit stated in the localizer's prompt was ignored (median 177 s of the budget), while a tool-less
localizer took 11-14 s in every run. Solve rates did not separate across arms (10-14 of 41), and giving the agent
the correct files did not raise them (held-out estimate -4.9 pp, one-sided upper bound +2.4 pp; not formally tested
because the pre-registered sequence stopped at the failed claim). We report the failed replication, a measurement
error caught by review, and what they imply for evaluating agent configurations on small task sets.

## 1. Introduction

Coding agents are now built around open models small enough for modest hardware, where each step is slow and the
budget per task is tight. The Kaggle Gemma 4 Developer Agent competition makes the configurator's position concrete:
a submission is a declarative ADK YAML configuration (prompts, sub-agents, tools, sampling settings) with no custom
code and no training of the base model.

When a configurator wants different behaviour, should they **ask** (write the rule into the prompt) or **enforce**
(build it into the structure)? Prior work suggests both matter (Section 6), but we know of no study that compares
the two on the same small model and tools, checks from transcripts whether the model did what it was asked, and
confirms the result on tasks not used for design.

Our contributions:

1. **Asking is followed literally, not in intent (confirmed).** The checkable part of a prompt rule (where to put
   scripts) was obeyed every time; the behaviour it served changed by an estimated +7 pp (95% CI -7 to +22).
2. **A structural effect on behaviour that looked strong on development tasks did not replicate.** A read-only
   first stage raised source-first starts on development tasks (p = 0.0001) but not on held-out tasks (p = 0.50).
3. **Limits held only when structural.** A length limit in the localizer's prompt was ignored; removing its tools
   enforced it in every run, including held-out.
4. **Under this budget, configuration did not move solve rates,** and neither did handing over the correct files.
5. **Two methodology lessons:** a path-based compliance metric produced a striking but false result until an
   independent review checked it against raw transcripts; and behavioural effects found by iterating on 30 tasks
   need a held-out test, because ours vanished in one.

## 2. Setting

**Model and serving.** Gemma 4 31B instruction-tuned, W4A16 QAT, served with vLLM 0.19.1 on 4x NVIDIA L4 (tensor
parallel 4), 32,768-token context. Temperature 0.2, top-p 0.95, at most 8,192 output tokens per step, thinking budget
4,096 tokens. The model is never trained: every run uses the competition sample submission's two LoRA adapters
unchanged.

**Harness.** The official harness (swegemma 0.2.11, adk_submission 0.2.13, google-adk 1.36.1) runs each task in a
sandbox with nine tools: shell, read, write, edit, status, submit and three code-graph tools. Per task the budget is
4.5 minutes of agent time and 100 tool calls; one shell command may run 120 s. If the agent stops without
submitting, the harness sends up to three "continue" nudges. The graded patch is the last submitted diff, or the
working tree. Grading runs hidden fail-to-pass and pass-to-pass tests.

**A fixed budget.** Seconds depend on hardware, so we treat the limit as one instance of a fixed per-task budget.
Steps take about 9-12 s here, so a task gets roughly 20-28 model steps; 11 to 18 of 30 development tasks and 22 to
28 of 41 held-out tasks end by timeout in every arm.

**Tasks.** The competition provides 129 practice tasks from four repositories. We validated each by grading the gold
patch (must pass) and an empty patch (must fail), three times; 71 tasks (FastAPI 29, Rich 42) passed. We used 30 for
development (FastAPI 13, Rich 17) and held out the other 41 (FastAPI 16, Rich 25), which were never run while
designing arms. The hidden leaderboard tasks come from other repositories.

## 3. Method

**Arms.** Every arm differs from the reference in one design choice.

| Arm | Change from reference | Question |
|---|---|---|
| Reference (E2) | official sample prompt, one agent | — |
| E3.1 | prompt adds: first edit to source by step 8; put scratch scripts in /tmp; no reproduction scripts before the first source edit | Does asking change behaviour? |
| E5 | SequentialAgent: a localizer with read, shell and graph tools but no edit tools (prompt: stop after about 8 tool calls; reply with files, functions, plan), then a fixer with the reference prompt and tools | Does enforcing change behaviour? |
| E5b | E5 with a tool-less localizer that answers once from the issue and the directory tree | Does a structural length limit hold? |
| ORACLE | reference agent plus the gold source files as task hints (development: files and heuristic function names; held-out: files only) | Is finding the code the bottleneck? |

The fixer in E5/E5b keeps the reference prompt verbatim after a three-sentence preamble pointing to the localizer's
notes. The reference's helper sub-agent (called once in 185 attempts) is not carried over.

**Measurements from transcripts.** Per task: solved; timeout; the first file write and its kind; whether a scratch
script went under /tmp; localizer time; and, for unsolved tasks, whether the final patch touched no source file,
only wrong source files, or the gold files. A write is a **source** write only if it targets a file inside a package
folder that is not a test or reproduction script; new files at the repository root, test files and anything under
/tmp are scratch. Shell redirects and `tee` count as writes after removing quoted strings and heredoc bodies.
**Source-first** means a task's first write was a source write; a task with no write counts as not source-first.

**Development phase.** Arms were designed and run one or two times on the 30 development tasks, with predictions and
decision rules committed before each run. Three near-identical reference runs (solved 11, 12, 13) form a pooled
reference. Behaviour shares were compared with Fisher exact tests, solve rates with exact McNemar tests and
task-level bootstrap intervals. These comparisons are exploratory: arms were added after seeing earlier results
(E5b was designed after E5), on the same 30 tasks.

**Held-out confirmation (pre-registered).** Before any held-out run, we committed the claims, the analysis code
(`analysis/heldout_tests.py`), and an amendment from an independent methodology review that set the tests below.
Each arm ran once on the 41 held-out tasks from notebooks built from one commit. Claims were tested in a fixed
sequence, each at one-sided alpha 0.05, stopping at the first failure:

- **C1 (manipulation check of asking):** among scratch-first tasks, E3.1 puts the script under /tmp in at least 80%,
  E2 in at most 20%, Fisher p < 0.05.
- **C2 (primary):** per task, source-first in E5b vs E2, one-sided exact McNemar p < 0.05; manipulation check: E5b
  localizer median at most 60 s. Expected power was about 0.6, so a null result is reported as "not detected".
- **C3:** the one-sided 95% bootstrap upper bound of the ORACLE minus E2 solve-rate difference is below +15 pp.

Tasks with a harness failure in any arm would be dropped; none occurred.

**C1 passed: asking is followed literally.** On held-out tasks E3.1 put every scratch-first script under /tmp
(20/20) and the reference none (0/25). The intent behind the rule moved little: source-first 13/41 vs 10/41,
estimate +7.3 pp with a 95% interval of -7.3 to +22.0.

**C2 failed: the structural effect did not replicate.** E5b started with a source edit on 11 of 41 tasks, the
reference on 10 (5 tasks favoured E5b, 4 the reference; p = 0.50). The arm worked as designed: its localizer took a
median of 13.8 s, well under the 60 s check, leaving the fixer almost the whole budget. The fixer, which has the
reference's tools and prompt, still wrote a scratch script first on 20 of 41 tasks. Among writing tasks, E5b's
source-first share fell from 55% on development tasks to 35%, while the reference stayed close (26% to 29%). Per
repository the direction was mixed (FastAPI 6 vs 4, Rich 5 vs 6). E5b also did not differ from ORACLE (estimate
-2.4 pp, CI -14.6 to +9.8), so even the location notes plus an instruction to start with an edit did not change the
fixer's habit on these tasks.

**C3 not tested.** The pre-registered sequence stopped at C2, so we do not claim C3. As an estimate only, ORACLE
solved 12/41 vs the reference's 14/41 (-4.9 pp, one-sided upper bound +2.4 pp), consistent with the development
result: knowing the right files did not raise solves within the budget.

**Solve rates.** Held-out solves were 14, 13, 10 and 12 of 41. No configuration we tried moved solve rate
detectably on either set; most unsolved tasks ran out of time (22 to 28 timeouts of 41) or ended with no source edit
(15 to 19), rather than editing the wrong files (0 to 2).

**Graph search vs grep (development only).** Before building a graph-based localizer we tested the competition's
`search_similar_code` against grep, with no model involved, using code names extracted from each issue. Graph search
put every gold file in its top five for 8 of 30 tasks, grep for 11; together 15. By our pre-registered rule the
graph-first arm was not run.

**A measurement error caught by review.** Our first definition counted any write outside /tmp as a source write,
which made E3.1 look like a dramatic backfire (scratch-first on 30 of 50 tasks vs 0 of 70). It was an artifact: the
reference agent's scripts lived at the repository root. An independent review of raw transcripts caught it; all
numbers here use the corrected definition.

## 5. Discussion

**Why did the development effect vanish?** We cannot tell from one held-out run per arm, and we did not plan a test
for it. Three explanations fit. First, selection: E5b was built after seeing E5 on the same 30 tasks, and its
development share came from tasks we had studied closely; an effect found while iterating on a small set is
inflated. Second, task mix: held-out Rich tasks went the other way, and 41 tasks give wide intervals (the E5b minus
E2 interval spans about 30 points). Third, sampling noise: two reference runs of the same configuration differed by
three tasks. The development reference itself replicated (26% vs 29%), which points to the E5b estimate as the
unstable one.

**What held up.** The literal-compliance finding replicated exactly, and the localizer's length limit held in all
three tool-less runs while the prompt-only limit failed. Both concern what the model is *able* to do, set by
structure or by a checkable rule. The behaviour we hoped to shift, whether the fixer starts by editing code, is a
habit of the fixer, and leaving the fixer's tools unchanged left the habit largely in place. A stronger structural
test would constrain the fixer itself, for example a first fixer stage that has edit tools but no shell, so the
first write cannot be a script; we leave this to future work.

**For practitioners.** Put hard limits in structure, not the prompt; expect prompt rules to be followed in their
checkable letter; do not expect location help or stage splits to lift solve rates when most failures are timeouts;
and confirm behavioural gains from a small development set on held-out tasks.

## 6. Related work

Agentless (arXiv 2407.01489) fixes localization, repair and validation as stages and matches agent systems with
strong models, without comparing the same model with and without staging. SWE-agent (2405.15793) shows interface
design matters as much as model choice. SWE-Gym (2412.21139) reports that open 7-32B models do far better in a
specialised workflow than as general agents, without measuring workflow compliance. AgentIF (2505.16944) finds weak
compliance with constraints stated in agent prompts; our C1 adds that checkable constraints can be followed exactly
while their purpose is not served. Budget-aware tool use (2511.17006) and SWE-Effi (2509.09853) study agents under
tool-call and time budgets. On localization, LocAgent (2503.09089) shows graph-guided search helps after
fine-tuning, with keyword search contributing most. SHERLOC (2606.24820) finds injected localization helps small models
without a hard time limit; our ORACLE estimates suggest the benefit shrinks when the budget binds. Statistics follow
Miller (2411.00640).

## 7. Limitations

One held-out run per arm, on 41 tasks from two repositories: power for C2 was about 0.6 at the development effect
size, so a smaller real effect could be missed; we report "not detected", not "no effect". Development comparisons
are exploratory and include a data-driven arm (E5b). C2 mixes three changes: a tool-less first stage, location notes
handed to the fixer, and an instruction to start by editing those locations; the fixer's preamble says the localizer
read the code, which is not true for E5b (wording kept so the arm is unchanged). E5 and E5b drop the reference's
rarely used helper. The held-out ORACLE gives files only, unlike the development ORACLE. The development reference
pools a first run with a larger output limit (16,384 tokens). The "source" definition is a path heuristic, revised
once after review. vLLM sampling is not deterministic, so tasks, not runs, are the unit. The two held-out pairs ran
about four hours apart because Kaggle allows two GPU sessions at once. One model, one hardware budget; the
practice repositories are not the hidden leaderboard repositories.

## 8. Conclusion

For a small open model under a fixed budget, asking gets literal compliance, and structure enforces limits that
prompts do not. But a stage split that looked like it changed the agent's working habit on 30 development tasks did
not on 41 held-out tasks, and no configuration or location help moved solve rates. The most reliable lessons are
methodological: check compliance metrics against raw transcripts, and confirm development-set effects on held-out
tasks with tests fixed in advance.
