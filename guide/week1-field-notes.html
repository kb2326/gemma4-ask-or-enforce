Section 3

The Kaggle token: one secret, two homes

Your Kaggle API token is like a password. Anyone who has it can act as you on Kaggle, including spending your daily submission. It starts with KGAT_, the newer token format Kaggle introduced, which works with the Kaggle CLI 1.8+ (you have 2.2.4).

It now lives in two places, both on your PC only:

  • .env in the project folder. Where you first saved it. Scripts can load it from here.
  • A Windows user environment variable named KAGGLE_API_TOKEN. Every new terminal and every new Claude Code session sees it automatically, so the CLI and MCP work without setup.
Where it must never goNot in git, not in .mcp.json, not pasted into chat. .gitignore excludes .env, and before the first commit we scanned every staged file for anything token-shaped. Nothing was found.

The MCP config uses a placeholder instead of the real value. Claude Code fills it in from the environment variable when it starts:

"Authorization": "Bearer ${KAGGLE_API_TOKEN}"   ← placeholder, safe to commit

This is why Claude Code needed a restart: a program only sees environment variables that existed when it started.

Section 5

GitHub as kb2326, and the two traps we hit

Your PC is logged into GitHub with two accounts: the work account (a work account) (the active one) and your personal kb2326. The goal was that this project only ever uses kb2326, without disturbing your work setup. Two things were set:

  • Who signs commits. This repo's own config says commits come from your name with the email 78557685+kb2326@users.noreply.github.com. That is GitHub's private "no-reply" address: commits count as yours without exposing your real email.
  • Who logs in when pushing. This took two fixes, shown below.

What went wrong, in plain terms

  1. Trap 1. Git for Windows ships its own login manager, set for the whole computer. It ran first and tried to open a sign-in window, so the command hung. We switched it off for this repo only. If you saw a GitHub sign-in pop-up today, it is safe to close it.
  2. Trap 2. The gh tool can hand logins to git, but only for its active account, which is your work account. Asked for kb2326, it returned nothing.
  3. The fix. A one-line helper in this repo's config. When git needs a login, it runs gh auth token --user kb2326, which reads kb2326's token from the Windows keyring (the secure password store), and passes it to git. We verified it: plain git push reaches the private repo as kb2326.
Why not just switch the active account?Switching with gh auth switch changes it for every project on the PC, so your work repos would start pushing as kb2326. The repo-local helper keeps the two worlds separate.

The first commit

Commit 967a63c holds 13 files: the baseline submission/, the README, the guide, .mcp.json, the submit guard, .gitignore and .gitattributes. The repo is private, and we plan to make it public for the paper, where the "Verifiability" criterion rewards shared code.

About .gitattributes: Windows ends text lines with two invisible characters (CRLF) and Linux with one (LF). Submissions run on Linux, where Windows line endings can break scripts, so this file keeps LF in the repo.

Section 7

Paper track rules

  • Format: a Kaggle Writeup of at most 3,000 words with a title and subtitle, abstract, introduction, methods and experiments, and related work with citations. A public notebook and an arXiv-style PDF are optional extras.
  • Originality: the work must be unpublished. The track is non-archival, so you can still send the paper to a conference later.
  • Judging: five criteria, 0–5 each, equal weight: Novelty, Quality (does it generalize?), Relevance, Verifiability (could someone reproduce it?) and Clarity.
  • Awards: Best Paper $15,000, Best New Resource $10,000 and Best New Application $10,000, shown at a Google event such as a NeurIPS expo workshop.
  • Hint from the hosts: papers that use the released code graph and embedding data are "highly encouraged".
  • Deadline: Nov 12, 11:59 PM UTC. Drafts that are saved but not submitted are ignored.
Why this suits usAbout 240 teams compete for three awards here, against about 3,040 teams in the main track. Our favourite question, whether the graph tools help a small model find the right code, is exactly the kind of work the hosts asked for.

Section 9

What the forum taught us

1. Some practice tasks fail even with the real fix

One competitor applied the developers' real fixes (the gold patches) to 6 practice tasks in the notebook environment. Only 2 passed. Some FastAPI tests import packages missing from the notebook (dirty_equals, inline_snapshot), and some Requests and httpx tests ran the installed library instead of the edited code. Staff said Docker scoring does not show these failures; the subprocess sandbox does.

So before trusting any practice score, we run a positive control: give every task its known-correct answer and see whether it passes.

2. Distillation from Claude or GPT is off the table

A grandmaster asked whether teams may train Gemma on transcripts from paid models. Staff answered: only within each model's license terms. Anthropic's and OpenAI's terms forbid using outputs to train other models, so our LoRA plan uses only Gemma's own successful runs or openly licensed data. This matches what we planned from the start.

3. The L4×4 machines are busy

Pinned threads cover queue delays, "Kaggle Error" submissions and runs that took 15 hours to score. Lesson: start runs early, never on deadline day.

4. Threads to read next

  • "Stronger models barely beat Gemma 4 31B in this harness." Someone tested much stronger models on the 124 public tasks, and they barely did better. The harness and its limits may be the real bottleneck, which is good material for the paper.
  • "Gemma 4 agent experiments: sampling, thinking, time limits, tool ablations." Someone else's early experiments, so we don't repeat them.
  • "The public leaderboard has exactly 58 tasks." So one solved task moves your score by about 0.017.
  • "The top of the leaderboard is dominated by those who trained LoRAs." A claim we will weigh against the mixed evidence in the main guide.

Section 13

Why we measure before changing anything

We cannot tell whether a change helps unless we know the score before the change, measured on the same tasks. A doctor runs tests before prescribing; this is the same idea. Engineers call it eval-driven development, and it is how serious agent teams work.

  1. Check the ruler. Make sure each practice bug can actually pass. (Section 16)
  2. Take a first reading. Run the unchanged agent. (Sections 17 and 19)
  3. Get the real number. Submit to the leaderboard, which uses hidden tasks. (Section 18)
  4. Read the failures. Transcripts show why Gemma fails, which tells us what to fix first.
  5. Change one thing, measure again, on the same tasks. Keep only what helps.
Where each step comes fromThe notebook flow is adapted from the official starter notebook. Checking each task with its real fix is how SWE-bench itself validates tasks. The forum showed why it is needed here. Measuring one change at a time is also what the paper's Verifiability criterion rewards.

The first try failed, and why

Both notebooks crashed in the first cell. The log said: cp312 … is not a supported wheel on this platform.

  • Cause: the harness packages are built for Python 3.12 (cp312 in the file names). Kaggle recently switched its default environment to Python 3.13, so the install was rejected.
  • Fix: pin the exact environment image the official notebook uses (Python 3.12.13), in each notebook's kernel-metadata.json.
  • Guard: the first cell now stops in seconds with a plain message if Python is ever wrong again.
  • Cost: a few minutes; it died during setup.
LessonWhen you copy someone's setup, copy the environment, not just the code. "Works on their machine, fails on mine" usually means a version difference.

  • 3 of 30 bugs flipped between identical runs: fastapi_11194 and rich_3043 became solved, rich_4077 became unsolved. About 10% of results are luck.
  • The rule that follows: a change must gain at least 3 bugs (net) before we keep it. From now on, 10 bugs count as "always solved", 3 as "flaky" (ignored) and 17 as "never solved".

Section 25 · Oct 18, 23:35

E1 result: not kept, and why that is useful

E1 changed one line on top of E2: the most Gemma may think before each action went from 4,096 to 2,048 tokens. The idea came from our first analysis, where failed bugs showed long silent thinking.

Run 1E0E2E1
Solved11121312
Ran out of time15111515

Longest single step (tokens)4,5384,2564,1392,262

Applying the keep rule

  • Gained: fastapi_9753, rich_3777. Lost: rich_3454. Net +1, which is inside the noise.
  • Targeted metric: timeouts stayed at 15; time per step fell only 7%, below the 20% bar.
  • Verdict: not kept. The setting goes back to 4,096, and E2 remains our current version.

Why it barely mattered

The cap did its job: the longest step dropped from about 4,500 to 2,262 tokens. But only about 2% of all steps ever think that long, and 95% stay under about 1,000 tokens. So the time is not lost in rare thinking bursts. It is lost to many ordinary steps: about 25 steps of about 10 seconds each fill the whole 4.5 minutes.

The lessonOur first diagnosis was right about the worst cases but wrong about where most of the time goes. Only measuring revealed that. A "failed" experiment that changes your understanding is a good result: it tells us the next lever is the number of steps, which is exactly what E3 (better instructions: edit early, stop wandering) targets.

Section 32

New words

API token
A long secret string that lets programs act as you on a website, like a password made for programs.
Environment variable
A named value the operating system hands to every program it starts. Programs started earlier don't see new ones.
MCP
Model Context Protocol: a standard way to plug a service's tools into an AI agent.
Project scope
A setting that applies to one folder only, not your whole computer.
Credential helper
A small program git asks for a username and password when talking to GitHub.
Keyring
Windows' secure store for passwords and tokens.
No-reply email
A GitHub address that credits commits to you without revealing your real email.
CRLF / LF
Invisible line-ending characters: Windows uses two, Linux one.
Baseline
The unchanged starting version that every improvement is measured against.
Wheelhouse
A folder of pre-downloaded Python packages, for installing without internet.
Subprocess sandbox
Running the agent's work in plain folders and processes when Docker is unavailable.
Gold patch
The real developer's fix for a task.
Positive control
A check that gives the known-correct answer to make sure the test itself works.
Distillation
Training a smaller model on a bigger model's outputs.
Quota
How much GPU time Kaggle lets you use per week.
Eval-driven development
Measure first, change one thing, measure again, keep what helps.
Negative control
A check that gives no fix at all, to make sure the test can fail.
Practice set
A fixed list of tasks (our 30) used for every experiment so results stay comparable.
Packaging notebook
The small notebook that builds and validates submission.zip.
Docker image
A saved snapshot of a whole software environment, here including Python 3.12.
Watcher
A small loop on your PC that asks Kaggle for a run's status every few minutes.
Pending submission
A submission waiting in Kaggle's queue or being scored.
Paired test
Compares two runs bug by bug, so only bugs whose result changed count. We use the exact McNemar test.
Confidence interval
The range the true effect probably lies in (95% sure). If it includes 0, the change may be luck.
Percentage points
A difference between two percentages. 40% to 50% is +10 points, which on 30 bugs is 3 more solved.
Held-out set
30 bugs never looked at while tuning, used once to check that improvements are not fitted to the practice bugs.
Replicate
Running the same version again to see whether a result repeats.
Pooled reference
Several near-identical runs of the kept version counted together (now Run 1, E0, E2), so one lucky run does not set the bar.
Flaky bug
A bug the same agent solves in some runs and not others. It shows luck, not skill.
Exploratory vs confirmatory
Exploratory: found by looking around. Confirmatory: predicted in writing first, then tested. Only the second counts as proof.
Arm
One version being compared in an experiment (for example E2, E5, ORACLE).
SequentialAgent
An ADK agent that runs its sub-agents one after another. E5 uses it for finder, then fixer.
ORACLE run
A practice-only run where the agent is told the correct files, to measure the best case for bug-finding.
Gate
A free check that must pass before an expensive run starts. Ours are checks 1–4.
Nudge
The harness's automatic "please continue" message when the agent stops without calling submit_patch.
