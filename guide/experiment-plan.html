Correction (Oct 24, after the code review)An independent review of our measurement code found that we counted any file outside /tmp as "real code". But today's agent usually writes its test script at the top of the repository (reproduce_issue.py), and the E3.1 prompt told Gemma to put scripts in /tmp. So the rule changed where scripts were saved, not whether Gemma wrote them first. We fixed the definition (real code = a file inside the project's package folders), recomputed every run, and withdrew the claim that the prompt rule "backfired". The corrected picture: first write was real code on 26% of bugs without the rule, 38% with it (not significant), and 60% with the finder → fixer structure (significant, p = 0.0001). Structure still beats asking, but less dramatically than we first reported.

Diagram 3 · The rule

How we decide to keep a change

Reference
The last kept version, pooled over the near-identical runs we have (now Run 1, E0 and E2).
Gain
A bug the new version solves that the reference never solved.
Loss
A bug the new version fails that the reference always solved.
Flaky
A bug the reference solved in some of its runs but not all (1 or 2 of 3). Ignored, because it tells us nothing.
Target metric
What the change aims at, for example timeouts for E1 or context crashes for E2. Since Oct 19 it must move more than it did between two identical runs, unless the effect is mechanical.
Statistics (Oct 19)
Every comparison also reports an exact paired test and a 95% confidence interval. Kept versions are checked once on a separate held-out set of 30 tasks.

Result

Held-out week: what the 41 new bugs said (Oct 31)

All four arms ran once on 41 bugs never used while designing, from one locked commit, with the tests and code fixed in advance. No task crashed. Solved: E2 14, E3.1 13, E5b 10, ORACLE 12.

TestWhat it asksResult
C1Does Gemma follow a literal rule ("put scratch scripts in /tmp")?pass 20 of 20 with the rule, 0 of 25 without
C2 (main)Does a finder with no tools make the fixer start with real code?fail 11 of 41 vs 10 of 41, p = 0.50. Not replicated
C3Does handing over the right files barely help?not tested the fixed order stops at C2. As an estimate: ORACLE 12 vs 14 solved
The main claim did not holdOn the 30 practice bugs the no-tool finder seemed to make the fixer start with real code (55% vs 26%). On new bugs it did not (35% vs 29%). The finder worked as designed (14 s), but the fixer kept its habit of writing a test script first. The practice result was most likely inflated by designing E5b on those same 30 bugs.

The spare run was not used: it could not change the verdict. The paper (Draft 3) now reports this honestly: asking is followed to the letter, limits hold only when built into the structure, the structural effect on behaviour did not replicate, and nothing moved the solve rate.
